# 시험·리뷰·문서화

## 시험
- 계산·규칙(순수 로직)은 spec의 수용 기준으로 **시험을 먼저** 쓰고, 실패를 확인한 뒤 구현한다.
- 커버리지 % 목표는 두지 않는다. 대신:
  - spec의 모든 FR·SC가 시험이나 QA 항목(qa.md의 C·H 번호)에 하나 이상 연결된다.
  - spec 3절의 경계·예외 상황은 모두 함수 시험 사례가 된다.
- 화면은 브라우저 미리보기로 직접 열어 확인하고 스크린샷 같은 증거로 보고한다. 사용자에게 확인을 떠넘기지 않는다.
- 시험이 실패하면 출력과 함께 그대로 보고한다.
- QA 결과는 증거 없이 통과로 적지 않는다. 확인하지 못한 것은 "확인 못 함"과 이유를 적고 따로 알린다.

## 리뷰
- plan 단계 끝: 자동 점검 — `ponytail-review`(코드), `web-design-guidelines`·`ui-ux-pro-max` 체크리스트(화면). 결과는 qa.md에 남긴다.
- 기능 끝: 사람 QA(판단이 필요한 것, 핵심 여정 한 바퀴). 사용자가 채팅으로 알려 준 결과를 qa.md에 기록한다.
- `code-review`는 큰 변경이나 사용자가 원할 때만 추가로 쓴다.

## 문서화
- 기획 문서, 출처 주석, Intent 변경 기록은 하네스 흐름대로 남긴다.
- `README.md`: 첫 기능이 끝날 때 만들고 기능이 끝날 때마다 고친다. 다섯 가지만 짧게: 무엇을 하는 앱인가(한 줄), 여는 법, 시험 명령, 지금 되는 기능, 기획 문서 위치(`docs/Intent.md`부터).
- 사용 설명서는 요청할 때만 만들고, 문장은 `humanize-korean`으로 다듬는다.
- 함수마다 설명을 다는 API 문서는 만들지 않는다. 이름과 타입 주석으로 대신한다.

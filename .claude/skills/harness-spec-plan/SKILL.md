# spec·plan 작성

기능 하나를 만들기 전에 두 문서를 순서대로 만든다.

```
docs/Intent.md ─┐
docs/요구서/   ─┤
docs/IA.md     ─┼─▶ spec.md (무엇을·왜) ─▶ [사용자 승인] ─▶ plan.md (어떻게) ─▶ [사용자 승인] ─▶ 개발
docs/journeys/ ─┤        FR-001, SC-001 번호        ────────▶  같은 번호로 단계·시험을 연결
docs/PRD.md    ─┤
docs/ERD.md    ─┘
```

- **spec**은 기술을 모르는 사람도 읽을 수 있게 **무엇을, 왜** 만드는지 쓴다. 언어·라이브러리·파일 이름을 쓰지 않는다.
- **plan**은 spec의 FR·SC 번호를 그대로 받아 **어떻게** 만들고 **어떻게 확인**할지 쓴다. plan에서 새 요구사항을 만들지 않는다.
- 두 문서 모두 모든 항목에 출처를 단다. 형식은 Intent와 같다: `[요구서 §6-1]`, `[IA SCR-001]`, `[UJ CUJ-01 2단계]`, `[PRD FR-003]`, `[ERD user]`, `[코드 src/ui/app.js]`.

참고한 방법: GitHub Spec Kit(spec·plan 템플릿, 확인 필요 표시 3개 제한, 품질 점검표), Kiro(요구사항 → 설계 → 작업 순서, 단계마다 승인, EARS 문장), Addy Osmani의 AI 에이전트용 스펙 가이드(항상/먼저 물을 것/절대 하지 말 것 3단 경계).

## 파일 위치

```
docs/specs/
└── {NNN}-{기능-이름}/        예: 001-로그인
    ├── spec.md
    └── plan.md
```
- 번호는 `docs/specs/` 안의 가장 큰 번호 + 1. 기능 이름은 요구서 제목을 하이픈으로 잇는다.
- 같은 기능의 spec이 이미 있으면 새로 만들지 않고 버전을 올려 고친다.

## 절차

### 1. 근거 읽기
1. `docs/Intent.md`를 읽는다 (`harness-intent` 절차 A). 6절 문서 지도에서 있는 문서를 확인한다.
2. 이 기능의 원문을 직접 읽는다: 요구서, IA(화면 ID·용어), 여정(단계·에러 복구·E2E 시나리오), PRD(FR·KPI·범위 밖), ERD(엔터티·필드). 없는 문서는 건너뛰고 spec·plan 머리말에 "없음"을 남긴다.
3. plan을 쓸 때는 현재 코드도 읽는다: 폴더 구조, 쓰는 언어와 라이브러리(`package.json`, `<script src>`), 시험 도구 유무, 코드 속 임시 처리(Q번호 주석).
4. 문서끼리 어긋나면 고르지 말고 사용자에게 묻는다.

### 2. spec 작성
`references/spec-template.md`를 읽고 그 규칙과 템플릿으로 쓴다.
- 요구서·PRD의 수용 기준을 FR로 옮길 때 원문 번호를 출처로 단다.
- 원문이 정하지 않은 동작은 지어내지 않는다. 6절 확인 필요 사항에 질문과 **가정**을 함께 쓴다.
- 본문 `[확인 필요]` 표시는 3개까지. 나머지는 가정으로 처리한다.

저장 뒤 점검표를 스스로 확인하고 스크립트를 돌린다:
```bash
py -X utf8 $HOME/.claude/skills/harness-spec-plan/scripts/check_spec_plan.py docs/specs/{NNN-기능}
```

### 3. spec 승인 받기
사용자에게 다음을 보여 주고 승인을 받는다. 승인 전에는 plan을 쓰지 않는다.
- FR 목록(번호, 한 줄, 우선순위)과 SC 목록
- 제외 범위
- 확인 필요 사항 중 답이 꼭 필요한 것 (최대 3개, 각각 선택지와 추천 답)

답을 받으면 spec을 고치고 상태를 "승인됨"으로 바꾼다.

### 4. plan 작성
`references/plan-template.md`를 읽고 그 규칙과 템플릿으로 쓴다.
- 기술과 버전은 **실제로 확인한 값**만 쓴다. 명령으로 확인한다(예: `node --version`, `package.json`, CDN 주소).
- 지금 쓰는 기술로 할 수 있으면 새 라이브러리를 들이지 않는다. 꼭 필요하면 새 의존성 기록에 쓰고 승인을 받는다.
- 첫 단계는 되도록 "지금 동작을 깨지 않고 구조 정리 + 시험 붙이기"로 잡는다.
- spec의 모든 FR·SC를 4절 요구사항 추적 표에 넣는다. spec 3절 경계·예외 상황은 모두 함수 시험 사례나 QA 항목이 된다.
- spec 제외 범위는 5절 "절대 하지 말 것"에 옮긴다.

저장 뒤 점검표를 확인하고 같은 스크립트를 다시 돌린다(이번엔 plan까지 검사). 통과할 때까지 고친다.

### 5. plan 승인 받기
단계 표, 새 의존성(있으면), 먼저 물을 것 목록을 보여 주고 승인을 받는다. 승인되면 상태를 "승인됨"으로 바꾼다.
승인 직후 `harness-qa` 절차 A로 같은 폴더에 `qa.md`를 만든다.

### 6. 마무리
- `docs/Intent.md` 6절 문서 지도에 spec·plan 행을 추가하거나 상태를 갱신하고, `harness-intent` 절차 B로 변경 기록을 남긴다.
- 사용자에게: 만든 파일 경로, FR·SC 개수, 스크립트 결과, 남은 확인 필요 사항, 다음 단계(plan 1단계부터 개발).

## 개발할 때 (plan 승인 뒤)
- plan 3절의 단계 순서대로 만든다. 한 단계가 끝 조건을 통과하기 전에 다음 단계로 가지 않는다.
- 코드 주석에 FR 번호를 단다. 예: `// FR-003 곧 도래 표시 (spec 001)`
- 단계가 끝날 때마다 `harness-qa` 절차 B로 QA와 회귀 확인을 하고 결과를 `qa.md`에 남긴다. 마지막 단계 뒤에는 절차 C로 사람 QA 목록을 준다.
- 개발 중 spec과 다른 동작이 필요해지면 코드를 먼저 바꾸지 말고 spec을 고쳐 승인받는다. plan의 체크박스는 끝낸 작업마다 체크한다.

## 참고 파일
- `references/spec-template.md` — spec 여섯 칸의 작성 규칙, 템플릿, 품질 점검표
- `references/plan-template.md` — plan 다섯 칸의 작성 규칙, 템플릿, 품질 점검표
- `scripts/check_spec_plan.py` — 칸 존재, 번호 중복, 확인 필요 표시 개수, spec↔plan 추적성, 버전 표기 검사

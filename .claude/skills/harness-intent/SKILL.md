# Intent 관리 (docs/Intent.md)

Intent는 이 프로젝트가 **무엇을, 왜, 어디까지** 만드는지 한곳에 모은 요약이자 색인이다. 세부 기준은 기획 문서에 두고, Intent는 그 기준을 출처와 함께 가리킨다. 그래서 개발자(코딩 에이전트 포함)는 Intent에서 출발해 출처를 따라 원문을 읽고 작업한다.

```
docs/문제정의.md ─┐
docs/요구서/     ─┤
docs/IA.md       ─┼─▶ docs/Intent.md ─▶ 개발 (코드에 출처 ID를 남김)
docs/journeys/   ─┤        ▲                │
docs/PRD.md      ─┤        └── 작업 결과 ───┘
docs/ERD.md      ─┘
```

## 다섯 칸과 각 칸의 출처

각 칸을 쓸 때 아래 문서를 우선 근거로 삼는다. 문서가 아직 없으면 있는 문서로 쓰고, 6절 문서 지도에 **없음**으로 남긴다.

| 칸 | 담을 내용 | 우선 근거 |
|---|---|---|
| 1. 문제 | 지금 무엇이 불편하거나 되지 않는지 | 문제정의 SCQA·네 칸, 여정 As-Is·페인포인트·감정 최저점, PRD 문제 정의 |
| 2. 기대 결과 | 해결되면 무엇이 어떻게 달라지는지, 성공 지표 | 요구서 수용 기준, 여정 To-Be·CUJ 성공 기준, PRD 목표·KPI·Must 요구사항 |
| 3. 영향 범위 | 누가 쓰는지, 어떤 화면·자료·코드·외부 시스템이 건드려지는지 | 문제정의 "누가", 여정 페르소나·터치포인트, IA 화면 ID·메뉴, ERD 엔터티, 현재 코드 |
| 4. 제약 | 예산, 기한, 지켜야 할 정책, 하지 않을 것, 고정된 규칙, 기술 제약 | 요구서 "하지 않을 것"·제약과 의존, PRD 범위 밖·NFR, ERD 제약조건 |
| 5. 열린 질문 | 아직 정하지 못한 것과 그 질문이 막고 있는 것 | 모든 문서의 열린 질문·확인 필요, 코드의 임시 처리 |

## 쓰는 규칙

1. **모든 문장에 출처를 단다.** 형식: `[문제정의 SCQA-A]`, `[요구서 §6-1]`, `[IA SCR-001]`, `[UJ CUJ-01 2단계]`, `[PRD FR-003]`, `[ERD user.email]`, `[spec 001 FR-003]`, `[plan 001 §3]`, `[코드 src/domain/date.js addMonths]`. 기능별 spec·plan(`docs/specs/`, `harness-spec-plan` 스킬)도 근거 문서이며, 6절 문서 지도에 기능마다 행을 둔다. 출처를 댈 수 없는 내용은 쓰지 않거나 5절 열린 질문으로 옮긴다.
2. **원문을 베끼지 않고 가리킨다.** Intent에는 한두 줄 요약만 둔다. 수용 기준·필드 정의·화면 상세는 원문에 둔다. 원문과 Intent가 다르면 원문이 맞다.
3. **기획 문서를 Intent로 대신 고치지 않는다.** 결정이 바뀌면 원문 문서를 먼저 고치고(해당 문서의 스킬이 있으면 그 스킬로), Intent는 그 결과를 따라간다. `docs/문제정의.md`는 사용자 확인 없이 고치지 않는다.
4. **문서끼리 어긋나면 고르지 말고 알린다.** 예: 요구서는 30일, PRD는 14일. 어느 쪽이 맞는지 사용자에게 묻고, 답을 받기 전에는 5절 열린 질문에 "문서 충돌"로 올린다.
5. **코드의 임시 처리도 열린 질문이다.** 코드가 미정 사항을 임시로 정해 둔 곳(주석에 Q번호가 있는 곳 등)은 5절에 "코드는 임시로 ~ 처리"라고 적는다.
6. **열린 질문은 번호를 유지한다.** 원문 문서의 질문 번호(요구서 Q4 등)를 그대로 쓰고, Intent에서 새로 생긴 질문만 이어지는 번호를 붙인다. 답이 나온 질문은 표에서 빼고 7절 변경 기록에 "Q4 해결: ~"으로 남긴다.

## 절차 A: 작업을 시작할 때 (개발 전)

1. `docs/Intent.md`를 읽는다. 없으면 절차 C로 먼저 만든다.
2. 6절 문서 지도 순서대로, 이번 작업과 관련된 원문을 **직접** 읽는다. 최소한 다음은 확인한다:
   - 요구서/PRD: 이 작업에 해당하는 수용 기준과 요구사항 ID, "하지 않을 것"
   - IA: 건드리는 화면의 화면 ID, 화면 형태, 용어 정의
   - 여정(UJ): 이 화면이 속한 여정 단계, 에러 복구, E2E 시나리오
   - ERD: 읽고 쓰는 엔터티·필드·제약조건
3. 사용자에게 작업 기준을 짧게 보고한다: 이번 작업이 근거로 삼는 출처 ID, 이번 작업에 걸린 열린 질문, 문서끼리 어긋난 곳.
4. 이번 작업을 막는 열린 질문이 있으면 사용자에게 묻는다. 답 없이 진행해야 하면 임시 처리를 정하고 그 사실을 코드 주석과 Intent 5절에 남긴다.

## 절차 B: 작업을 마칠 때 (매 작업마다)

1. 이번 작업으로 바뀐 것을 다섯 칸에 반영한다.
   - 새로 정해진 것 → 해당 칸에 출처와 함께 추가
   - 답이 나온 질문 → 5절에서 빼기
   - 새로 생긴 질문·임시 처리 → 5절에 추가
   - 새로 건드린 화면·자료·파일 → 3절에 추가
2. 새로 생기거나 고쳐진 기획 문서가 있으면 6절 문서 지도의 상태를 갱신한다.
3. 머리말의 `최종 갱신` 날짜와 버전을 올린다. 다섯 칸 중 하나라도 내용이 바뀌면 소수점 버전(v0.1 → v0.2)을 올린다. 변경 기록만 추가되면 버전은 그대로 둔다.
4. 7절 변경 기록에 한 줄을 남긴다: 날짜, 버전, 작업 이름, 바뀐 내용(출처 ID 포함).
5. 다섯 칸에 바뀐 것이 없는 작업(오타 수정 등)도 7절에 "Intent 변경 없음"으로 한 줄 남긴다.

## 절차 C: Intent.md를 새로 만들거나 크게 다시 쓸 때

1. `docs/` 아래 기획 문서를 모두 찾는다: 문제정의, 요구서, IA(`IA.md`/`IA.xlsx`), 여정(`journeys/`), PRD, ERD. 현재 코드도 훑어 구현 상태와 임시 처리를 찾는다.
2. 아래 템플릿으로 작성한다. 이미 있으면 덮어쓰지 말고 버전을 올려 고친다.

```md
# Intent: {프로젝트 이름}

- 상태: {초안|합의됨} (v{버전})
- 최종 갱신: {YYYY-MM-DD}
- 근거 문서: {있는 문서 목록}
- 아직 없는 문서: {없는 문서 목록}

> 요약과 색인이다. 세부 기준은 출처 문서에 있다. 개발할 때는 [출처]를 따라가 원문을 읽는다.

## 1. 문제 (Problem)
## 2. 기대 결과 (Proposed outcome)
## 3. 영향 범위 (Affected users and systems)
## 4. 제약 (Constraints)
## 5. 열린 질문 (Open questions)
| # | 질문 | 막고 있는 것 | 출처 |
## 6. 문서 지도
| 순서 | 문서 | 경로 | 상태 | 개발할 때 여기서 가져올 것 |
## 7. 변경 기록
| 날짜 | 버전 | 작업 | 바뀐 내용 |
```

## 마무리 확인

Intent.md를 저장한 뒤 다음을 확인한다:
- [ ] 다섯 칸(1~5절)이 모두 있고, 비어 있는 칸은 "확인 필요"와 그 이유를 적었다
- [ ] 모든 항목에 `[출처]`가 있다
- [ ] 출처로 단 문서와 ID가 실제로 존재한다 (없는 화면 ID나 요구사항 ID를 지어내지 않았다)
- [ ] 문서 지도의 "있음/없음"이 실제 `docs/` 상태와 같다
- [ ] 7절 변경 기록에 이번 작업이 남아 있다

# QA (docs/specs/NNN-기능/qa.md)

```
plan 승인 ─▶ 절차 A: QA 목록 등록 ─▶ [plan 단계 끝마다] 절차 B: Claude QA + 결과 기록
          ─▶ [기능 끝] 절차 C: 전체 회귀 + 사람 QA 목록 제공 ─▶ 절차 D: 사람 결과 기록 ─▶ 완료
```

- **C 항목**: Claude가 직접 확인한다. 함수 시험, 브라우저 미리보기 조작, 코드 검사로 확인할 수 있는 것.
- **H 항목**: 사람만 판단할 수 있는 것. 두 종류만 넣는다.
  1. **판단**: 화면이 보기 좋고 읽기 쉬운지, 용어가 현장에서 쓰는 말과 맞는지, 실제 일에 쓸 만한지.
  2. **핵심 여정 한 바퀴**: 핵심 여정(CUJ)을 처음부터 끝까지 직접 해 보고, 결정적 순간(MOT)에 기대한 느낌이 드는지.

## 규칙
1. **증거 없이 통과로 적지 않는다.** 증거는 시험 이름과 통과 개수, 스크린샷 파일, 명령 출력 요약, 확인한 화면 상태 같은 것이다.
2. Claude가 확인할 수 없는 것(실제 휴대폰, 회사 PC, 실제 업무 데이터, 인쇄 등)은 C 항목에 `확인 못 함`과 이유를 적는다. 통과로 바꾸지 않고, 사용자에게 보고할 때 따로 알린다.
3. **결과는 바꿔 쓰지 않고 쌓는다.** 실패한 항목을 고친 뒤 다시 확인하면, 결과 칸을 `실패 → 통과 (재확인 {날짜})`처럼 남기고 "실패와 조치" 표에 한 줄을 남긴다.
4. **모든 SC는 C 항목이나 H 항목에 한 번 이상 나온다.** spec 3절의 경계·예외 상황은 C 항목이 된다.
5. 사람이 실패로 알린 내용이 버그가 아니라 spec에 없던 새 요구라면, 고치기 전에 spec을 고칠지 묻는다(`harness-spec-plan`).
6. plan 4절에는 QA 항목을 다시 적지 않는다. 요구사항 추적 표의 "시험 이름 / QA 번호" 칸에 C·H 번호만 적는다.

## 절차 A: QA 목록 등록 (plan 승인 직후)
1. spec(FR, SC, 3절 경계·예외), plan(3절 단계, 4절 테스트 전략), 여정(`docs/journeys/`의 CUJ, 여정 명세의 단계와 에러 시나리오)을 읽는다.
2. 아래 템플릿으로 `qa.md`를 만든다. C 항목마다 확인할 plan 단계를 정한다.
3. H 항목은 이 시점에 초안으로 적어 둔다(결과 칸은 비움). 절차 C에서 실제 화면에 맞게 다듬는다.
4. plan 4절 추적 표의 QA 번호 칸을 채운다.
5. C·H 개수와 SC가 빠짐없이 들어갔는지를 사용자에게 보여 주고 승인을 받는다.

## 절차 B: 단계 QA (plan 단계 하나가 끝날 때마다)
1. 그 단계에 걸린 C 항목을 직접 확인한다.
   - 함수 시험: 프로젝트 CLAUDE.md "명령"의 시험 명령을 돌린다.
   - 화면: 브라우저 미리보기로 열어 누르고, 읽고, 필요하면 스크린샷을 남긴다.
   - 화면 파일 점검: `web-design-guidelines`와 `ui-ux-pro-max`의 납품 전 체크리스트로 접근성·대비·반응형 항목을 확인하고, 지적 사항(`파일:줄`)을 증거로 남긴다.
   - 코드 점검: 단계 끝마다 `ponytail-review`로 변경분을 본다(고치지 않는 보고만). 고칠 것은 이 절차의 실패와 조치로 처리한다.
2. 앞 단계에서 통과한 항목도 다시 확인한다(회귀). 함수 시험은 전체를 돌린다.
3. 결과·증거·날짜를 `qa.md`에 적는다. 실패하면 고치고 다시 확인한 뒤 "실패와 조치"에 남긴다.
4. 사용자에게 짧게 보고한다: 통과/실패/확인 못 함 개수, 실패와 조치, 확인 못 한 이유. 그다음 단계 승인을 받는다.

## 절차 C: 기능 끝 (마지막 plan 단계가 끝날 때)
1. 모든 C 항목을 다시 확인한다.
2. H 항목을 실제 화면에 맞게 다듬는다. 항목마다 다음을 적는다.
   - 준비: 앱 여는 방법, 넣어 둘 자료
   - 할 일: 번호 붙인 짧은 동작
   - 보고 판단할 것: "예/아니오"로 답할 수 있는 질문
3. 상태를 `사람 QA 대기`로 바꾸고, 사람 QA 목록을 채팅으로 준다.
   - 맨 위에는 앱 여는 방법과 걸리는 시간 어림을 적는다.
   - 결과는 "H-01 통과", "H-02 실패: 글자가 작음"처럼 알려 달라고 안내한다.

## 절차 D: 사람 결과 기록 (사용자가 결과를 알려 줄 때)
1. 사용자가 말한 결과·메모·날짜를 H 항목에 그대로 적는다(사용자의 말을 바꾸지 않는다).
2. 실패는 "실패와 조치"에 올리고 고친다(규칙 5 확인). 고친 뒤에는 관련 C 항목을 다시 확인하고, 그 H 항목만 다시 봐 달라고 요청한다.
3. 모든 H 항목이 통과하면 상태를 `완료`로 바꾸고, `harness-intent` 절차 B로 Intent 문서 지도와 변경 기록을 갱신한 뒤 커밋을 제안한다.

## 마무리 확인
- [ ] 모든 SC가 C나 H 항목에 있다
- [ ] 통과로 적은 C 항목마다 증거가 있다
- [ ] 확인 못 한 항목과 그 이유를 사용자에게 알렸다
- [ ] H 항목은 판단과 핵심 여정, 두 종류뿐이다
- [ ] 머리말 상태와 요약 개수가 표와 같다

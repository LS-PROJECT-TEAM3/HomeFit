# PRD 검토와 공격 검토

## 1. 검토 체크리스트
**빈칸 먼저, 그다음 뺄 것** 순서로 돌려준다.

결정을 막는 빈칸
- [ ] 문제에 근거(데이터·인터뷰·VOC)가 있거나, 없으면 가설로 표시되어 있는가?
- [ ] KPI에 현재값·목표값·기간이 있는가?
- [ ] 핵심 사용자가 문제·Job 기준으로 정의되어 있고 2~3개 이하인가?
- [ ] 사용자 그룹마다 6요소 가치 제안(누가·왜·이전·어떻게·이후·대안)이 있는가?
- [ ] 가치 제안의 "어떻게"를 기능 요구사항이 실현하고, "이후"를 KPI가 측정하는가?
- [ ] CUJ 단계가 실제 IA 화면 ID로 이어지는가?
- [ ] 여정의 모든 MOT에 Must 요구사항과 그 실패를 막는 수용 기준이 있는가?
- [ ] 여정의 페인포인트마다 요구사항·이후 범위·하지 않을 것·가정 중 하나로 처리되어 있는가?
- [ ] CUJ에 에러 복구 경로가 있고, 해피 패스만 요구사항으로 만들지 않았는가?
- [ ] 여정에서 "가설"이던 감정·수치가 PRD에서 사실처럼 쓰이지 않았는가?
- [ ] Must 요구사항마다 검증 가능한 수용 기준이 있는가?
- [ ] "하지 않을 것"이 적혀 있고 Won't 요구사항과 일치하는가?
- [ ] 가정과 미결 질문이 본문 사실과 섞이지 않고 분리되어 있는가?
- [ ] 개인정보·법적 이슈와 외부 종속성이 빠지지 않았는가?

뺄 수 있는 것
- 결정을 바꾸지 않는 배경 설명, IA·여정·디자인 문서와 중복되는 화면 설명·여정 표 복사본, "TBD" 섹션, 첫 버전 검증과 무관한 Should/Could

## 2. 공격 검토 (Red-team)
정중한 피드백만 통과한 계획은 실제 출시에서 깨진다. 계획을 무너뜨릴 가정을 찾아 공격하고 가장 싼 검증 방법을 준다.

절차
1. 모든 주장을 뽑고, **틀리면 계획이 무너지는 것(핵심 가정)**만 남긴다.
2. 각 가정을 가장 강한 형태로 세운 뒤 공격한다. 허수아비 공격 금지.
3. 실패 조건을 "**~라면 실패한다**"로 쓴다.
4. (틀렸을 때 영향) × (틀릴 가능성) × (검증 비용의 낮음) 으로 순위를 매긴다.
5. 근거가 탄탄한 부분은 분명히 인정한다. 약점을 지어내지 않는다.

출력 형식
```markdown
## 공격 검토: [계획 한 줄 요약]

### 핵심 가정 (순위순, 3~5개)
- **가정:** [핵심 주장]
  - **실패 조건:** [구체적, 반증 가능하게]
  - **이번 주에 모을 증거:** [구체적으로]
  - **중단 기준:** [수치 기준]
  - **가장 싼 테스트:** [가장 작은 실험]

### 잘 설계된 부분
### 판단할 수 없었던 부분
```

포트폴리오·사이드 프로젝트라면 "가장 싼 테스트"를 혼자 할 수 있는 수준(지인 5명 테스트, 경쟁 앱 리뷰 100개 분류, 랜딩 페이지 대기 신청 수 등)으로 제안한다.

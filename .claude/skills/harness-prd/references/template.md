# PRD 템플릿

표기: **[간결]** 기본 PRD에 항상 포함 · **[상세]** 상세판 요청 시 또는 해당 내용이 결정에 필요할 때만.
각 섹션 아래 질문은 체크리스트다. 이번 건에 중요한 것만 답하고 나머지는 건너뛴다.

```markdown
# PRD: [제품/기능명]

## 0. 문서 정보 [간결]
| 항목 | 내용 |
|---|---|
| 작성자 | |
| 작성일 / 버전 | YYYY-MM-DD / v0.1 |
| 상태 | 초안 · 검토 중 · 확정 |
| 참조 문제정의 | docs/문제정의.md |
| 참조 IA | docs/IA.md (vX) / docs/IA.xlsx |
| 참조 여정 | docs/journeys/ 의 고객 여정 지도 / CUJ 문서 (버전·날짜) |
| 이해관계자 [상세] | 이름 · 역할 · 코멘트 (모르면 행 자체를 뺀다) |

변경 이력 [간결: 2번째 버전부터]
| 날짜 | 버전 | 변경 내용 | 이유 |
|---|---|---|---|

## 1. 요약 [간결]
무엇을, 누구를 위해, 왜 지금 만드는지 2~3문장.

## 2. 배경과 문제 [간결]
- 무엇에 관한 일인가? 어떤 문제가 있나?
- 근거: 사용자 여정의 페인포인트·감정 최저점·As-Is 불편(단계 이름과 근거 종류 표시), 설문·인터뷰·지표·VOC(반복 키워드)·사용성 이슈 / 신규라면 시장 변화·경쟁 제품 동향. 출처를 옆에 적는다.
- 문제는 1~3개로. 여정에서 KPI와 연결되는 가장 아픈 구간부터.
- 왜 지금인가? 무엇이 바뀌었거나 새로 가능해졌나?
- 근거가 없으면 "가설"로 표시하고 8번 가정 목록에 올린다.

## 3. 목표와 성공 지표 [간결]
- 비즈니스 목표: (예: 가입 전환 증가, 상담 비용 절감)
- 사용자 목표: 사용자가 이 제품으로 이루려는 결과

| KPI | 현재값 | 목표값 | 측정 방법 | 기간 |
|---|---|---|---|---|
| 예: 상품 상세 → 가입 완료 전환율 | 4% (가설) | 8% | 이벤트 로그 퍼널 | 출시 후 90일 |

1~3개. CUJ의 OEC(핵심 지표)를 대표 KPI로 삼고, 나머지 터치포인트 지표는 7번 수용 기준으로 보낸다. 구체적이고 측정 가능하며 기한이 있게(SMART). 현재값과 목표값을 비교할 수 있게 쓴다. "만족도 개선" ✗ → "NPS 32 → 45, 출시 90일 내" ✓

## 4. 핵심 사용자 [간결]
| 사용자 그룹 | 겪는 문제 / 해야 할 일(Job) | 지금의 해결 방법 | 제약 | 여정 출처 |
|---|---|---|---|---|
- 인구통계가 아니라 문제·Job으로 나눈다.
- 첫 버전은 2~3개 그룹까지. 나머지는 "이후 대상"으로 한 줄.

## 5. 가치 제안 [간결: 항상 포함, 사용자 그룹마다 1개]
6요소 JTBD 템플릿 (Paweł Huryn & Aatir Abdul Rauf). 제품이 아니라 고객에서 출발한다.
### [사용자 그룹명]
- **누가(Who)**: 4번의 그룹
- **왜(Why)**: 해내려는 일, 그것을 막는 문제
- **이전(What before)**: 지금 어떻게 하고, 무엇이 불편한가
- **어떻게(How)**: 우리 해결책이 그 일을 해내는 핵심 방식 (기능 목록은 7번)
- **이후(What after)**: 좋아진 결과, 새로 가능해지는 것
- **대안(Alternatives)**: 우리가 없으면 쓸 것, 그래도 우리를 고를 이유

> 가치 제안 문장: 1~2문장

[상세] 대안 대비 가치 곡선(Value Curve) 표.

## 6. 핵심 사용자 여정 (CUJ) [간결: 1~3개]
사용자 여정 스킬의 CUJ 문서에서 3번 KPI와 직접 연결되는 것만 고른다 (없으면 IA 유저 플로우에서). 해결책이 아니라 사용자의 목표와 문제에 초점을 둔다.

### CUJ-01: [여정 이름]
- 사용자 그룹 / 목표(JTBD):
- 유형: High-Traffic / High-Dollar / OEC 기반
- 사용자 스토리: "(사용자 유형)인 나는 (목적)을 위해 (필요한 것)을 원한다."
- 시나리오:
  1. [화면명] (`화면 ID`) — 사용자가 하는 일 / 시스템 반응
  2. **[MOT]** [화면명] (`화면 ID`) — 성공/이탈이 갈리는 지점, 지금 감정(점수)과 이유
  3. ...
     - [조건]이면 → [분기] (`화면 ID`)
- 성공 기준: 사용자가 [결과]에 [N단계/N초] 안에 도달
- 에러·복구: 실패 조건 → 사용자가 보는 것 → 복구 경로 (여정 명세의 에러 시나리오에서). 해피 패스만 쓰지 않는다.
- 검토한 대안 [상세]: 이 CUJ를 풀 다른 방법과 고르지 않은 이유 한 줄씩. 결정 자체는 8번에.

[상세] 사용자 여정 지도는 복사하지 말고 10번에 링크. 필요하면 감정 곡선 한 줄 요약만 (예: 계산 +1 → 인증 -2 → 완료 +2).

## 7. 기능 요구사항 [간결: Must·Should / 상세: 전체]
| FR ID | 요구사항 | 여정 출처 | 관련 화면 ID | 우선순위 | 수용 기준 |
|---|---|---|---|---|---|
| FR-01 | | CUJ-01 MOT / 페인포인트 "…" | `PD_010102_PG` | Must | 무엇이 되면 완료인가 (검증 가능한 문장, 여정 지표·성공 기준 활용) |

`여정 출처`: CUJ ID와 단계(MOT 여부), 또는 여정 지도의 단계·페인포인트. 여정과 무관한 요구사항(법적 필수 등)은 이유를 쓴다.

우선순위 (MoSCoW):
- **Must**: 없으면 사용자가 핵심 목표를 이룰 수 없다
- **Should**: 꼭은 아니지만 사용자가 매우 필요로 한다
- **Could**: 있으면 좋은 선택 기능
- **Won't (이번엔)**: 이번 버전에서 하지 않는다 → 9번 "하지 않을 것"과 일치

Must에는 수용 기준을 반드시 쓴다. MOT를 다루는 Must는 그 MOT의 실패(이탈 원인)를 막는 기준을 포함하고, CUJ의 에러 복구 요구사항도 Must에 넣는다. PM 혼자보다 개발자와 함께 작성·검토한다.

[상세] 비기능 요구사항: 성능, 보안, 개인정보, 접근성, 지원 환경(브라우저/OS), 로그·분석 이벤트.

## 8. 결정·제약·가정 [간결: 가정과 미결 질문은 항상]
- 주요 결정과 절충안: 무엇을 골랐고 무엇을 버렸나, 이유는? 나중 기능을 위해 지금 특정 방식을 택했다면 그것도 기록
- 기술 제약 / 리소스·예산 [상세]
- 종속성: 다른 팀, 외부 서비스(IA 개발 구분 `외부연동` 화면 참고)
- 개인정보·법적 고려 (수집 항목, 동의, 관련 규제)
- **가정과 미결 질문**: 믿지만 증명되지 않은 것 / 아직 알아내야 할 것. 각 항목에 확인 방법·담당 한 줄

## 9. 출시 계획 [간결]
- 1차 범위: (Must + 선택된 Should)
- 처리 안 한 여정 페인포인트: 이후 범위 또는 하지 않을 것으로, 이유와 함께
- 이후 범위: 2차 이후
- **하지 않을 것(Non-goals)**: 이번에 명시적으로 하지 않는 것
- 일정: 상대 기간으로 (예: 설계 1주 → 개발 3주 → 베타 1주). 정확한 날짜는 팀과 합의 후
- [상세] 유관부서 준비: 마케팅·영업·CS가 출시에 맞춰 준비할 것, 배포 방식(단계적 공개, A/B)

## 10. 참고 문서 [간결: 링크만]
- IA / 메뉴구조도 / 화면목록
- 고객 여정 지도(HTML) / CUJ / 여정 명세
- 와이어프레임·스토리보드, UX 리서치 결과, 레퍼런스
- [상세] Q&A, 정책 문서
```

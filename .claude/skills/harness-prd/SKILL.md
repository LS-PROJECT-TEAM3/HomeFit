# PRD 작성 (IA → 사용자 여정 → PRD)

PRD는 팀이 **무엇을 먼저, 왜** 만드는지 합의하는 문서다. 개발자·디자이너·의사결정자가 몇 분 만에 읽고 착수할 수 있어야 하고, 기획→디자인→개발→테스트→출시 전 단계에서 "요구사항을 충족했는가"를 확인하는 기준이 된다.

이 스킬은 앞 단계 스킬의 산출물을 이어받는다.

```
docs/문제정의.md       harness-ia          harness-journeys            harness-prd
무엇이 문제인가   →    어디에 무엇이 있나  →  누가 어떻게 겪고 어디서 막히나  →  왜·무엇을·어디까지 만드나
(SCQA, 네 칸)          (docs/IA.md)           (docs/journeys/)                  (docs/PRD.md)
```

기반: phuryn/pm-skills 의 `create-prd` · `write-prd` · `red-team-prd` (MIT, `LICENSE-pm-skills-MIT`). 코드스테이츠 블로그의 PRD 7가지 구성 요소와 Omar Eduardo Fernández의 WHY 기반 작성법을 반영해 확장했다.
이 사본은 `prd-kr` 를 하네스용으로 고친 것이다. 바뀐 점: `docs/문제정의.md` 를 입력에 더하고, 입력·출력 경로를 `docs/` 로 맞췄다. 원본 두 출처에서 빠져 있던 다음 단계 제안(사전 부검, 개발용 사용자 스토리 분해)과 CUJ의 "검토한 대안"을 보강했다.

## 원칙

1. **WHY 먼저.** 모든 기능에는 그 기능이 풀 사용자 문제와 비즈니스 근거가 붙어야 한다. "지금 꼭 해야 하는 일인가"를 확인해 만들 필요 없는 기능에 시간을 쓰지 않게 하는 것이 PRD의 첫 역할이다.
2. **여정이 근거, PRD는 결정.** 사용자 여정은 "무슨 일이 일어나는지"를, PRD는 "그래서 무엇을 만들고 무엇을 안 만드는지"를 쓴다. 여정의 모든 페인포인트는 PRD에서 **요구사항이 되거나, 하지 않을 것/이후 범위로 명시적으로 미뤄져야** 한다. 조용히 사라지면 안 된다.
3. **해결책이 아니라 사용자 필요에 집중.** CUJ는 특정 기능이 아니라 사용자의 목표와 문제를 중심으로 쓴다. 기능에 매달리면 근본 문제에서 멀어진다.
4. **기본은 간결하게.** 첫 PRD는 첫 버전을 결정하고 착수하는 데 막힘이 없을 만큼만. 표를 빼면 대략 2~3쪽. 할 말이 적은 섹션은 한두 줄. "TBD"로 채우지 않는다. 상세판은 요청할 때만.
5. **지어내지 않는다.** 모르는 것은 본문에 사실처럼 쓰지 않고 `가정과 미결 질문`에 둔다. 여정 문서의 근거 표시(직접 사용/데이터/가설)를 그대로 물려받는다. 가설이면 PRD에서도 가설이다.
6. **중복하지 말고 연결한다.** IA·여정·와이어프레임에 이미 있는 내용은 복사하지 않고 화면 ID, CUJ ID, 문서 링크로 참조한다.
7. **살아있는 문서.** 개발 중 범위·일정 절충이 생기면 PRD를 갱신하고 변경 이력에 남긴 뒤 관련 팀에 공유한다.
8. **쉬운 말.** 짧은 문장, 전문용어 최소화. 영어 용어는 처음 한 번만 괄호로 병기.

## 프로세스

### 1. 입력 수집
다음을 이 순서로 찾아 읽는다:
- **문제정의**: `docs/문제정의.md` — SCQA와 네 칸, 확인 필요 목록. 다른 입력과 어긋나면 그 사실을 알리고, 어느 쪽을 따를지 사용자에게 묻는다. 문제정의 문서는 고치지 않는다
- **IA**: `docs/IA.md`, `docs/IA.xlsx`(`IA`·`화면목록` 시트), 화면 JSON — 화면 ID, 우선순위(MVP/2차/보류), 개발 구분, 용어 정의, "확인된 사항"
- **사용자 여정**: `docs/journeys/` 아래 고객 여정 지도(`maps/`), CUJ(`critical/`), 여정 명세, 여정 JSON(`build_journey_map.py` 입력 형식)
- 리서치, VOC, 지표 자료가 있으면 함께

문제정의 → PRD 대응 (여정·IA에 같은 내용이 더 구체적으로 있으면 그쪽을 쓴다):

| 문제정의 | PRD 위치 |
|---|---|
| 상황(S), 걸림돌(C), 네 칸의 "무엇이" | 2. 배경과 문제 |
| 네 칸의 "얼마나" | 3. KPI의 현재값 (확인 필요면 `(가설)`) |
| 네 칸의 "누가" | 4. 핵심 사용자 |
| 질문(Q), 지금의 답(A) | 1. 요약, 9. 1차 범위 |
| 확인할 것 하나, 확인 필요 목록 중 IA·여정에서도 답이 안 난 것 | 8. 가정과 미결 질문 |

없는 것이 있으면 진행은 하되 한 줄로 알린다. IA가 없으면 화면 ID 연결을, 여정이 없으면 문제 근거와 CUJ가 약해진다. 필요하면 해당 스킬로 먼저 만들자고 제안한다.

### 2. 빈칸만 질문
아래 세 가지 중 입력(특히 여정 문서)에 없는 것만, **한 메시지에 최대 3개** 묻고 그 답변에서는 PRD를 쓰지 않는다:
1. **사용자 문제**: 누가, 어떤 상황에서, 얼마나 불편한가? 근거가 있나?
2. **대상 사용자**: 누구를 위해 먼저 만드나? 지금은 어떻게 해결하나?
3. **성공 기준**: 무엇이 얼마나 바뀌면 성공인가?

여정 문서가 충분하면 대부분 이미 답이 있다. 시장·경쟁사·규제처럼 웹에서 찾을 수 있는 것은 묻지 말고 조사한다. 조사 결과는 결정을 바꾸는 경우에만 본문에 넣고 출처를 옆에 적는다. 사용자가 "그냥 써줘"라고 하면 빈칸을 가정으로 표시하고 진행한다.

### 3. 쓰기 전 생각 (문서에는 넣지 않음)
어떤 문제를, 누구를 위해 푸는가? 성공을 어떻게 아는가? 그것을 검증하는 가장 작은 첫 버전은? 여정의 어느 MOT를 이번 버전이 반드시 지켜야 하는가? IA의 MVP 화면이 정말 첫 버전에 필요한가? 아이디어가 너무 크면 단계를 나누고 1단계만 명세한다.

### 4. PRD 작성
`references/template.md` 를 읽고 그 구조로, `references/mapping.md` 의 변환 규칙에 따라 작성한다.

| # | 섹션 | 핵심 | 주요 출처 |
|---|---|---|---|
| 0 | 문서 정보·변경 이력 | 상태, 참조 IA·여정 버전 | — |
| 1 | 요약 | 무엇을, 누구에게, 왜 지금 (2~3문장) | — |
| 2 | 배경과 문제 | 근거 데이터, 출처, 왜 지금 | 여정 페인포인트·감정 최저점·As-Is |
| 3 | 목표와 성공 지표 | 비즈니스 목표 → KPI → 현재값 vs 목표값 (SMART) | CUJ의 OEC, 터치포인트 지표 |
| 4 | 핵심 사용자 | 문제·Job 기준, 첫 버전 2~3개까지 | 여정 페르소나 |
| 5 | 가치 제안 | 사용자 그룹마다 6요소 JTBD (항상 포함) | JTBD 목표, As-Is, 비교 대상 |
| 6 | 핵심 사용자 여정 (CUJ) | 1~3개, 단계별 화면 ID, MOT, 사용자 스토리 | CUJ 문서, IA 유저 플로우 |
| 7 | 기능 요구사항 | FR ID, 여정 출처, 화면 ID, MoSCoW, 수용 기준 | 여정 기회·MOT, 여정 명세 성공 기준·에러 시나리오 |
| 8 | 결정·제약·가정 | 절충안, 기술 한계, 종속성, 개인정보·법적 이슈, 가정 | 여정 근거 "가설" 항목 |
| 9 | 출시 계획 | 1차·이후 범위, **하지 않을 것**, 상대 일정, 유관부서 준비 | 미처리 페인포인트 |
| 10 | 참고 문서 | IA·여정 지도·화면목록·와이어프레임·리서치 링크 | — |

**섹션 간 정합성이 PRD의 뼈대다.** 5번 가치 제안의 "어떻게(How)"를 7번 기능이 실현하고, "이후(What after)"를 3번 KPI가 측정한다. 6번 CUJ의 각 단계와 MOT는 7번 요구사항과 IA 화면으로 이어진다. 이 줄이 끊기면 다른 것보다 먼저 고친다.

### 5. 추적성 검사 (IA나 여정 파일이 있을 때)
PRD를 저장한 뒤 실행한다:
```bash
py -X utf8 $HOME/.claude/skills/harness-prd/scripts/check_traceability.py docs/PRD.md --ia docs/IA.md --journey docs/journeys/critical/<CUJ>.json [--journey <여정 파일2>]
```
- IA 파일: `.json` | `.xlsx` | `.md`, 여정 파일: `.json` (여정 지도 입력 형식) | `.md`
- IA 검사: 없는 화면 ID 참조, 요구사항 없는 MVP 화면, 우선순위 불일치, 수용 기준 빠진 Must
- 여정 검사: Must 요구사항이 없는 **MOT 단계**, PRD에 흔적이 없는 **페인포인트 단계**, PRD에 없는 CUJ ID, PRD에 반영되지 않은 여정 지표, IA에 없는 여정 화면 ID
- 스크립트는 화면 ID·이름의 **흔적**만 본다. 통과해도 페인포인트가 실제로 해결됐는지는 `references/mapping.md` 의 페인포인트 처리 원칙으로 직접 확인한다.
- 문제가 있으면 고치고 다시 돌린다. 결과 요약을 답변에 한두 줄로 알린다.

### 6. 저장과 마무리
- `docs/PRD.md` 로 저장. 이미 있으면 덮어쓰지 말고 변경 이력에 버전을 올려 고친다.
- 답변에서(문서 밖에서) **일부러 뺀 것**을 한 줄로 알린다 (예: 경쟁사 분석, 비기능 요구사항 상세, 운영 정책).
- 다음 단계 중 맞는 것을 1~2개 제안한다: 상세판 확장, 범위 더 줄이기, PRD 공격 검토(`references/review.md`), 사전 부검(pre-mortem: 출시 후 실패했다고 가정하고 그 경로를 거꾸로 추적), 개발용 사용자 스토리 분해(Must 요구사항마다 스토리와 수용 기준으로), 이해관계자 공유용 요약, 바이브코딩용 구현 순서(Must 요구사항을 CUJ 단계 순서대로 묶어 구현 프롬프트로), E2E 테스트(여정 명세의 에러 시나리오 → 테스트).
- 이해관계자(개발·디자인·영업·CS)에게 공유해 의견을 받으라고 권한다. 1인 프로젝트라면 실제 사용자 2~3명에게 핵심 가정만 확인해도 된다.

## 기존 PRD 검토
`references/review.md` 의 체크리스트로 본다. **빈칸(결정을 막는 누락)을 먼저**, 그다음 **뺄 수 있는 것**을 돌려준다. 요청이 있으면 같은 파일의 공격 검토(Red-team) 형식으로 핵심 가정을 공격하고 가장 싼 검증 방법을 제시한다.

## 참고 파일
- `references/template.md` — PRD 템플릿(간결판·상세판 구분 표시). 작성 전에 읽는다.
- `references/mapping.md` — IA·여정 산출물 → PRD 섹션 변환 규칙. 입력 문서가 있으면 읽는다.
- `references/review.md` — 검토 체크리스트와 공격 검토 형식.
- `scripts/check_traceability.py` — PRD ↔ IA ↔ 여정 추적성 검사.
- `assets/example_IA_screens.json`, `assets/example_CUJ-보험가입.json`, `assets/example_PRD-보험가입.md` — IA → CUJ → PRD로 이어지는 예시 한 벌.

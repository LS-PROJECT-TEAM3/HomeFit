# 사용자 여정 설계 (고객 여정 지도 / CUJ / 여정 명세)

**명세는 기능을 검증하고, 여정은 경험을 검증한다.** 모든 기능이 명세를 통과해도 경험은 형편없을 수 있다. 여정은 사용자가 실제로 어떻게 움직이는지, 단계마다 어떤 감정인지, 실수에서 어떻게 회복하는지, 느린 네트워크·중단 같은 현실 조건에서 어떻게 되는지를 담는다.

원본: alinaqi/maggy 의 `user-journeys` (MIT). 고객 여정 지도와 CUJ 방법론을 더해 기획·분석 단계까지 확장했다.
이 사본은 `user-journeys-kr` 를 하네스용으로 고친 것이다. 바뀐 점: `docs/문제정의.md` 와 `docs/IA.md` 를 맥락의 출발점으로 읽고, 산출물을 `docs/journeys/` 에 저장한다. `references/cuj.md` 에 감정 표시 방법과 여러 채널에 걸친 CUJ 사례를 보강했다.

## 먼저 모드를 고른다

세 문서는 범위와 목적이 다르다. 사용자가 "유저 저니 그려줘"라고만 해도 어떤 결과가 필요한지 먼저 판단하고, 애매하면 추천 모드와 함께 한 번 묻는다.

| 모드 | 범위 | 핵심 질문 | 결과물 | 참고 파일 |
|---|---|---|---|---|
| **A. 고객 여정 지도** | 넓다. 이용 전→중→후 전 과정, 여러 채널 | 사용자는 단계마다 무엇을 하고 어떻게 느끼며, 어디서 불편한가? | 단계 × (행동/터치포인트/생각·감정/페인포인트/기회) 표, 감정 곡선, 페르소나 | `references/journey-map.md` |
| **B. CUJ** | 좁다. 핵심 과업 하나 | 이게 실패하면 제품이 망가지는 흐름은 무엇이고, 어디가 Moment of Truth인가? | 사용자·목표(JTBD)·최소 과업, 핵심 터치포인트 4~6개와 지표 | `references/cuj.md` |
| **C. 여정 명세** | 화면/기능 단위 단계 | 단계별 성공 기준·에러 복구가 충족되는가? | 단계별 사용자 행동/시스템 반응/성공 기준/마찰, 에러 시나리오, 테스트 | `references/journey-spec.md` |

추천 기준:
- **기존 서비스 분석, UX 케이스 스터디, 포트폴리오** → A (필요하면 그중 가장 중요한 흐름 하나를 B로 깊게).
- **새 서비스 기획 초기, 리디자인, 지표 하락 원인 찾기, 팀 우선순위 합의** → B로 핵심 여정 3~5개를 고른 뒤, 각각을 C로 구체화.
- **개발 중/구현 직전, 코드베이스가 있음** → C (+ `references/e2e-testing.md`).
- 큰 그림부터 필요하면 A → B → C 순서로 이어서 쓴다. 이때 A에서 발견한 페인포인트가 B의 MOT 후보가 되고, B의 핵심 터치포인트가 C의 단계가 된다.

## 공통 프로세스

### 1. 맥락 파악
- **`docs/문제정의.md` 를 먼저 읽는다.** 이 프로젝트의 기획 출발점이다. 각 항목은 다음처럼 쓴다:

  | 문제정의 항목 | 여정에서 쓰는 곳 |
  |---|---|
  | 네 칸의 **누가** | 페르소나 / CUJ의 핵심 사용자 |
  | 네 칸의 **언제**, SCQA의 **상황(S)** | 시나리오와 여정의 시작점 |
  | SCQA의 **걸림돌(C)**, 네 칸의 **무엇이** | As-Is 행동·불편. 감정 곡선의 최저점 후보 |
  | 네 칸의 **얼마나** | As-Is 기준치(빈도·소요 시간). To-Be 지표의 비교 기준 |
  | SCQA의 **질문(Q)**, **지금의 답(A)** | To-Be 행동. CUJ의 목표(JTBD)와 MOT 후보 |
  | **확인할 것 하나**, **확인 필요 목록** | 근거 수집 항목. 답이 없으면 해당 감정·수치를 `가설`로 표시 |

- 문제정의 문서는 고치지 않는다. 읽기만 한다. 여정을 쓰며 새로 알게 된 사실은 여정 문서의 근거 칸에 적고, 문제정의 갱신은 사용자에게 제안만 한다.
- `docs/IA.md` (또는 `docs/IA.xlsx`) 가 있으면 읽고, 여정 단계에 **화면 ID**를 연결한다. 그러면 여정과 화면 설계가 같은 언어로 이어진다. IA에 없는 화면이 여정에 필요하면 IA 보완 후보로 따로 적는다.
- 무엇을 분석/설계하는지, 신규인지 기존 서비스인지, 결과를 어디에 쓸지(팀 공유, 포트폴리오, 개발 기준)가 문제정의로 분명하지 않으면 확인한다.
- 코드베이스가 있으면 라우팅·주요 화면을 훑어 실제 흐름을 기준으로 삼는다. 상상한 흐름이 아니라 실제 흐름에서 출발한다.

### 2. 근거 수집
여정은 근거가 있어야 설득력이 있다. 가능한 근거를 사용자와 함께 정한다:
- **직접 사용(필드 테스트)**: 실제로 처음부터 끝까지 써보며 단계별 행동·감정을 기록. 여러 명이 각자 써보고 페르소나별로 비교하면 더 좋다.
- **정량 데이터**: 단계별 이탈률, 전환율, 소요 시간, 오류율. 숫자는 *무엇이* 일어나는지 알려준다.
- **정성 데이터**: 인터뷰, 리뷰·앱스토어 평점, 고객센터 문의, 설문. 이야기는 *왜* 일어나는지 알려준다.
- 근거가 없다면 "가설"로 표시하고, 검증 방법(사용성 테스트, 데이터 확인 항목)을 함께 적는다. 근거 없는 감정·수치를 사실처럼 쓰지 않는다.

### 3. 인터뷰
질문마다 **추천 답을 함께 제시**하고 2~3개씩 묶어 묻는다. 모드별 필수 질문은 각 참고 파일에 있다.

### 4. 작성
해당 모드의 참고 파일 템플릿으로 작성한다. 파일로 저장할 때 경로:
```
docs/journeys/
├── maps/          # A. 고객 여정 지도 (페르소나별)
├── critical/      # B. CUJ (3~5개) → 각 CUJ의 C 명세
├── common/        # 자주 쓰는 일반 경로
└── edge-cases/    # 에러 복구, 예외 경로
```
채팅 환경이면 답변 또는 파일로 제공한다.

### 5. 시각화 (모드 A, B)
여정 지도는 표만으로는 감정 흐름이 잘 안 보인다. 데이터를 JSON으로 정리해 HTML 여정 지도를 만든다:
```bash
py -X utf8 $HOME/.claude/skills/harness-journeys/scripts/build_journey_map.py journey.json journey_map.html
```
- JSON과 HTML은 해당 문서 옆(`docs/journeys/maps/` 또는 `docs/journeys/critical/`)에 같은 이름으로 둔다.
- `as_is_label` 에는 문제정의의 기존 방식(예: "라벨 직접 확인")을, `evidence` 에는 근거 수준(직접 사용 / 인터뷰 / 가설)을 적는다.
- 입력 형식은 `assets/example_journey.json` 참고 (A·B 공용, `mode` 필드로 구분).
- 단계 열 × 행 레이아웃, 감정 곡선(-2~+2), As-Is/To-Be 비교, MOT 강조, 단계별 지표를 한 화면에 그린다. 인쇄하면 PDF로도 쓸 수 있다.

### 6. 점검
- **해피 패스만 그리지 않았는가?** 최소 1개의 실패·복구 경로를 넣는다.
- 문제정의의 걸림돌(C)이 As-Is에서 가장 아픈 구간으로 드러나고, To-Be에서 그 구간이 해소되는가? "얼마나"의 기준치와 비교할 지표가 있는가?
- 감정·수치마다 근거(직접 사용/데이터/가설)가 표시돼 있는가?
- 모든 페인포인트가 기회(개선 아이디어) 또는 지표로 이어지는가?
- CUJ라면 3~5개를 넘지 않는가? 모든 게 critical이면 아무것도 critical이 아니다.
- 다음 단계(화면 설계 수정, 사용성 테스트 계획, E2E 테스트, 지표 대시보드)를 한두 줄로 제안한다.

## 피해야 할 것 (원본 계승 + 보강)
- 해피 패스만 작성 / 기능 명세를 여정이라고 부르기
- 시간 무시 (여정에 걸리는 시간을 재지 않음)
- 데스크톱만 고려 / 감정 생략 / 지표 없음
- 한 번 쓰고 갱신 안 함 (사용자 행동이 바뀌면 여정도 바꾼다)
- 한 여정에 여러 목표(JTBD)를 섞기
- 목표 달성에 영향 없는 단계까지 다 넣기
- 근거 없는 감정을 사실처럼 쓰기

# 정보구조 설계 (IA / 메뉴구조도 / 화면목록)

이 스킬은 서비스의 뼈대를 정의한다. 기획(무엇을, 누구를 위해)과 화면 설계·개발 사이에 위치하며, 결과물은 디자이너·개발자·(바이브코딩이라면) 코딩 에이전트가 그대로 작업 기준으로 쓸 수 있어야 한다.

원본: julianoczkowski/designer-skills 의 `information-architecture` (Apache-2.0). 한국 실무 문서 구분과 화면 ID 체계를 더해 확장했다.
이 사본은 `information-architecture-kr` 를 하네스용으로 고친 것이다. 바뀐 점: `docs/문제정의.md` 를 맥락의 출발점으로 읽고, 산출물을 `docs/` 에 저장한다.

## 핵심 개념: 세 문서는 목적이 다르다

IA, 메뉴구조도, 화면목록은 생김새가 비슷해서 자주 혼동된다. 사용자가 "IA 써줘"라고 해도 실제로 필요한 것이 다른 문서일 수 있으므로, 목적을 먼저 확인한다. 상세 규칙은 `references/document-types.md` 를 읽는다.

| 문서 | 목적 | 범위 | 언제 |
|---|---|---|---|
| **IA (정보구조도)** | 화면 간 관계·흐름·속성을 정의 | 최종 화면까지 모든 단계 (예: 회원가입 시작~완료 전 화면) | 화면이 많고 복잡할 때, 신규 구축 시 작업 우선순위를 정할 때, 디자이너·개발자가 화면 간 연관성을 모를 때 |
| **메뉴구조도** | 전체 메뉴·서비스 구성을 한눈에 | 메뉴/서비스 진입점까지만, 보통 최대 3 Depth (사이트맵과 유사) | 리뉴얼 시 추가·변경·삭제를 한눈에 볼 때, 대형 서비스의 전체 윤곽을 먼저 볼 때, 소규모 서비스에서 IA 일부를 대체할 때 |
| **화면목록** | 모든 화면을 고유 ID로 관리 | 모든 화면, 경로(Location)와 ID 중심으로 간결하게 | 화면 수가 많고 여러 작업자가 화면 ID로 소통할 때, IA가 너무 무거워 가독성이 떨어질 때 |

기본 추천:
- 소규모(화면 ~20개, 1인/바이브코딩): **메뉴구조도 + 간단한 IA**. 화면목록은 IA 표의 ID 열로 대체.
- 중규모 이상 또는 협업: **IA + 화면목록**, 리뉴얼이면 메뉴구조도에 상태 라벨 추가.

## 프로세스

### 1. 맥락 파악
- **`docs/문제정의.md` 를 먼저 읽는다.** 이 프로젝트의 기획 출발점이다. 각 항목은 다음처럼 쓴다:

  | 문제정의 항목 | IA에서 쓰는 곳 |
  |---|---|
  | 네 칸의 **누가** | 주 사용자. 사용자 유형별 진입점·로그인 여부 판단 |
  | 네 칸의 **언제**, SCQA의 **상황(S)** | 사용자가 서비스를 여는 순간 = 첫 화면(0 Depth)이 보여 줄 것 |
  | SCQA의 **걸림돌(C)**, 네 칸의 **무엇이** | 화면 구조가 없애야 할 수고. 핵심 목표까지의 Depth를 줄이는 근거 |
  | SCQA의 **지금의 답(A)** | 첫 기능 = 우선순위 `MVP` 화면. 나머지는 `2차` 또는 `보류` |
  | **확인할 것 하나**, **확인 필요 목록** | 3단계 인터뷰 질문으로 옮긴다. 답이 없으면 추천 답을 가정으로 쓰고 비고에 `(가정)` 표시 |

- 문제정의 문서는 고치지 않는다. 읽기만 한다. 인터뷰에서 새로 확인된 사실은 IA 문서의 "확인된 사항" 절에 적고, 문제정의 갱신은 사용자에게 제안만 한다.
- `docs/문제정의.md` 가 없으면 `.design/*/DESIGN_BRIEF.md` 같은 기획 문서를 찾는다. 그것도 없으면 무엇을 만드는지, 주 사용자는 누구인지, 신규 구축인지 리뉴얼인지 묻는다.
- 포트폴리오/학습 목적이라면 그 사실을 기록해두고, 문서에 "설계 의도" 설명을 조금 더 넣는다 (면접에서 설명할 수 있도록).

### 2. 기존 구조 탐색 (코드베이스가 있을 때)
- 라우팅: Next.js `app/`·`pages/`, React Router, Vue Router, SvelteKit, Streamlit `pages/`, 정적 HTML 파일
- 네비게이션: header, sidebar, GNB/LNB, breadcrumb, footer, 하단 탭
- 레이아웃, 페이지 디렉터리, URL 패턴(슬러그, 동적 세그먼트, 쿼리 파라미터), 데이터 계층(API 라우트, DB 모델)
- 이미 있는 구조는 확장·개선한다. 기존 구조를 무시한 새 설계를 제안하지 않는다. 리뉴얼이라면 기존 화면에 `유지/변경/삭제`, 새 화면에 `신규` 라벨을 붙인다.

### 3. 인터뷰
질문마다 **추천 답을 함께 제시**해서 사용자가 "네" 한마디로 넘어갈 수 있게 한다. 한 번에 다 묻지 말고 2~3개씩 묶는다. 문제정의의 "확인 필요 목록" 중 화면 구조에 영향을 주는 것(예: 다룰 대상의 수, 관리 단위, 강조 표시 기준, 화면에 보여 줄 항목)을 먼저 묻고, 화면과 무관한 것은 건너뛴다. 이어서 최소한 다음을 다룬다:
- 어떤 문서가 필요한가? (위 표 기준으로 추천)
- 사용자가 가장 자주 찾거나 하는 일은? 빈도순으로.
- 허용 가능한 Depth는? (기본 추천: 핵심 목표까지 3 Depth 이내. 단계가 깊을수록 목표까지 거칠 화면이 많아진다. 단, 꼭 필요한 화면은 줄이지 않는다.)
- 로그인 전/후로 보이는 화면이 다른가? 사용자 유형(일반/관리자 등)별 진입점이 다른가?
- 시간이 지나며 늘어나는 콘텐츠와 고정 콘텐츠는?
- 사용자가 시간의 80%를 보내는 화면은?
- 일정·리소스가 제한적이라면, 이번에 개발할 범위(MVP)는?

### 4. 산출물 작성
`references/document-types.md` 의 템플릿으로 마크다운 문서를 작성하고 `docs/IA.md` 로 저장한다 (엑셀을 만들면 `docs/IA.xlsx`). 문서 맨 위에 `근거: docs/문제정의.md` 를 적고, MVP 화면마다 비고에 문제정의의 어느 항목(예: "지금의 답")에서 나왔는지 짧게 남긴다.

IA 표는 다음 열을 기본으로 한다 (목적에 따라 열을 추가·삭제 가능):

| 열 | 내용 |
|---|---|
| 화면 ID | `references/screen-id-guide.md` 규칙 |
| 0~3 Depth | 메인(홈)을 0 Depth로 시작 |
| 화면명 | 중복 없는 고유 이름 |
| 형태 | 페이지 / 팝업 / 탭 / 링크(외부) / 모달·바텀시트 |
| 로그인 | 필요 / 불필요 |
| 개발 구분 | 개발(기능·데이터 필요) / 콘텐츠(정적) / 외부연동 — 우선순위 판단용 |
| 우선순위 | MVP / 2차 / 보류 |
| 상태 | 신규 / 유지 / 변경 / 삭제 (리뉴얼 시) |
| URL | 웹이면 경로 패턴 |
| 비고 | 진입 조건, 연결 화면 등 |

원본 템플릿의 섹션(네비게이션 모델, 콘텐츠 우선순위, 유저 플로우, 용어 정의, 공통 컴포넌트, 콘텐츠 증가 대응, URL 전략)도 필요한 만큼 함께 작성한다. 소규모라면 유저 플로우와 용어 정의는 빼지 말고, 나머지는 줄여도 된다.

### 5. 엑셀 산출 (요청 시 또는 화면 15개 이상일 때 제안)
실무에서 IA·화면목록은 엑셀로 주고받는 경우가 많다. 화면 데이터를 JSON으로 정리한 뒤 스크립트로 만든다:

```bash
py -X utf8 $HOME/.claude/skills/harness-ia/scripts/build_ia_workbook.py screens.json output.xlsx
```

- 입력 형식은 `assets/example_screens.json` 참고.
- 시트: `작성가이드`(약어·형태 코드 범례), `IA`, `메뉴구조도`(3 Depth까지, 진입점만), `화면목록`(경로 + ID).
- 화면 ID는 엑셀 수식(`CONCATENATE`)으로 생성되므로 Depth 번호를 고치면 ID가 자동 갱신된다. 단, 이미 공유된 ID는 바꾸지 말아야 하므로 확정 후에는 값으로 고정하라고 안내한다.
- 스크립트가 중복 ID를 검사해 경고한다. 경고가 나오면 고친 뒤 다시 만든다.

### 6. 마무리 점검
- 같은 화면명이 두 번 나오지 않는가? 같은 개념에 다른 용어를 쓰지 않았는가?
- 핵심 목표(예: 가입, 예약, 업로드)까지의 Depth가 합의한 한도 안인가?
- 모든 팝업·탭이 부모 화면을 갖는가?
- 문제정의의 "지금의 답"을 MVP 화면만으로 끝까지 해낼 수 있는가? 걸림돌(C)이 말하는 수고(예: 직접 둘러보기)를 MVP 화면이 대신하는가?
- 다음 단계(화면 설계, 바이브코딩 프롬프트)를 한두 줄로 제안한다. 바이브코딩이라면 "화면목록의 MVP 행을 순서대로 구현 요청" 같은 식으로 연결해준다.

# 데이터-표 구성과 고른 이유

> DB 표의 큰 묶음, 표 사이 관계, 그렇게 고른 이유, 계산해서 쓰는 값.

## 내용
- 저장소는 Supabase(PostgreSQL). 로그인은 Supabase Auth의 `auth.users`를 쓰고 모든 사용자 표는 행 단위 권한(RLS)을 켠다. (근거: docs/ERD.md · 머리말 저장소)
- 표 묶음: 사용자와 직접 입력(profiles, policy_conditions, homes, indoor_measurements, interest_areas, interest_homes(v1.9), notification_settings, push_subscriptions(v1.12)) → [[데이터-사용자 입력 표]], 수집(sources, runs, run_steps, source_items, observations) → [[데이터-수집 표]], 사건과 대응·기록·관리자·챗봇·채점(incidents, response_plans, incident_actions, schedule_items, knowledge_chunks, audit_logs, wiki_chunks, chat_logs, eval_results, notice_follows, notice_summaries, notifications, llm_calls) → [[데이터-사건·대응·기록 표]]. (근거: docs/ERD.md · ## 관계도, ## 엔터티)
- 고른 이유 1: 수집 값을 공통 표 하나(observations)에 같은 모양(시각·대상·지표·값·바뀐 정도·출처)으로 담아, 출처가 늘어도 표를 새로 만들지 않는다. 원본은 raw로 남긴다. (근거: docs/ERD.md · ## 이렇게 고른 이유 1)
- 고른 이유 2: 공고·정책 한 건을 source_items로 따로 두어 공고 ID로 중복 사건을 막고 content_hash로 바뀜을 비교한다. (근거: docs/ERD.md · ## 이렇게 고른 이유 2)
- 고른 이유 3: 사건 세 종류를 incidents 한 표에 둔다. 다른 것은 facts(jsonb)와 incident_type뿐이다. (근거: docs/ERD.md · ## 이렇게 고른 이유 3)
- 고른 이유 4: 승인·거절과 관리자 수정을 지우지 않는 표에 쌓아 "누가, 언제, 왜"를 남기고, 승인 기록은 사용자 본인만 추가할 수 있게 한다. (근거: docs/ERD.md · ## 이렇게 고른 이유 4) v1.13의 승인 취소·거절 취소도 이 원칙대로 앞 줄을 고치지 않고 새 줄로 쌓는다. (근거: docs/ERD.md · #### incident_actions, 변경 기록 v1.13)
- 저장하지 않고 계산하는 값: 이슬점·추정 창 표면 온도, 최근 3개월 중간값·거래 수(결과는 incidents.facts에), 마감까지 남은 날 수, 맞는 공고 목록, 출처별 연속 실패 수, 하루 질문 수(chat_logs 조회), 사건 기준값(10%, ±20%, 48시간, 습도 기준은 코드 설정). (근거: docs/ERD.md · ## 저장하지 않고 계산하는 값)
- 화면마다 어떤 표를 읽고 쓰는지는 ERD "화면별로 읽고 쓰는 표"에 있다. 예: 위키 챗봇(AD_070700_TB)은 저장소 `wiki/` 파일과 chat_logs를 읽고 chat_logs를 쓴다(ERD v1.10). (근거: docs/ERD.md · ## 화면별로 읽고 쓰는 표)
- 실제 DB 대조 기록(P3-16): 2026-11-17 마이그레이션 0001~0005, 0010·0011 뒤 표·칸 이름이 문서와 같았다. 2026-11-18 오후 마이그레이션 0001~0017·0020 뒤 실제 DB의 표 20개와 표별 칸 수가 문서·마이그레이션과 같았고(선우, 대시보드 읽기만), 저녁에 0019로 audit_logs가 생겼다(PR #11). (근거: docs/ERD.md · ## 실제 DB 대조)
- v1.11(2026-11-19, 마이그레이션 0021, spec 019): interest_homes에 입주 전 점검 칸 두 개, 하자 기록 표 defect_records(내 집에 여럿, HOMES ||--o{ DEFECT_RECORDS), 사진 저장소 defect-photos와 접근 규칙. 관심 주택(interest_homes)도 "내 행만 읽기·쓰기, 관리자 전체 읽기" 묶음에 들어갔다. 자세한 칸은 [[데이터-사용자 입력 표]]. (근거: docs/ERD.md · 머리말 최종 갱신, 변경 기록 v1.11, 권한 표)
- v1.12(2026-11-20, 승인 "모두 승인", 마이그레이션 0022, spec 021): push_subscriptions 표(PROFILES ||--o{ PUSH_SUBSCRIPTIONS "웹 푸시 기기")와 접근 규칙, notifications.channel에 `web_push`. PRD v1.20 FR-35. ([[기능-021 웹 푸시 알림]]) (근거: docs/ERD.md · 머리말 최종 갱신, ## 관계도, 변경 기록 v1.12)
- v1.13(2026-11-23, 승인 "추천대로 승인", spec 023): notice_follows 본인 지우기 권한, incident_actions.action에 `cancel_approve`·`cancel_reject`, 승인 취소 때 그 승인으로 만든 schedule_items를 지움. 이유: 잘못 누른 팔로우·승인을 "새 공고"·"승인 대기"로 되돌려, 일정에는 본인이 승인한 것만 남게 하려고. ([[기능-023 결정 되돌리기]]) (근거: docs/ERD.md · 변경 기록 v1.13) (근거: docs/specs/023-결정-되돌리기/spec.md · 1. 해결하려는 문제)
- v1.14(2026-11-23, 승인 "승인", spec 024, 마이그레이션 없음): interest_homes.move_in_checklist 설명만 넓힘(항목 메모와 내 항목을 같은 객체에). 이유: 표·칸을 더하지 않고 지금 칸을 그대로 쓰며 예전 값도 읽기 위해. ([[기능-024 점검 내 항목과 항목별 메모]]) (근거: docs/ERD.md · 변경 기록 v1.14) (근거: docs/specs/024-점검-내항목-메모/spec.md · 관련 자료)
- v1.15(2026-11-23, 승인 "추천대로 승인", spec 025, 마이그레이션 0024): homes에 gas_usage_mj·gas_bill_month·gas_tariff_region. 이유: 고지서 한 장을 한 번 넣어 두면 난방비 탭에서 12개월 예상 난방비를 다시 넣지 않고 보이기 위해(PRD v1.24가 v1.14의 "저장 안 함"을 바꿈). ([[기능-025 도시가스 12개월 난방비]]) (근거: docs/ERD.md · 변경 기록 v1.15) (근거: docs/specs/025-도시가스-12개월-난방비/spec.md · 1. 해결하려는 문제)
- v1.16(2026-11-23, 승인 "승인", spec 026, 마이그레이션 0025): notice_follows·schedule_items에 정책(`youth_policy`) 줄, 정책을 일정에 넣는 DB 함수. 표 모양은 그대로. 이유: 공고와 같은 표·같은 칸을 써서 정책도 팔로우하고 내 일정에 넣기 위해. ([[기능-026 정책 팔로우와 내 일정]]) (근거: docs/ERD.md · 머리말 최종 갱신, 변경 기록 v1.16) (근거: docs/specs/026-정책-팔로우-일정/spec.md · 관련 자료)

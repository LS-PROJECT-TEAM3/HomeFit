## 1. 한눈에

한 줄: 관리자가 가짜 자료를 넣으면 수집 → 사건 → 알림이 생기고, 사용자가 승인해야 일정에 들어가며, 흐름 화면과 채점이 그것을 숫자와 그림으로 보여 준다.

| 장면 | 화면 | 청중이 보는 것 | 평가 항목 |
|---|---|---|---|
| 1 | 관리자 > 수집 현황·오류 | 정기 수집이 쌓이는 모습, 연속 실패 수 | P3-17 |
| 2 | 관리자 > 시뮬레이터 | 가짜 공고를 넣고 한 번에 돌림 | P3-06 |
| 3 | 관리자 > 흐름 화면 | 방금 돈 실행이 상자·화살표로 그려짐 | P3-08 |
| 4 | 사용자 화면 (가상 계정) | 알림 → 승인 → 내 일정. 관리자는 대신 승인 못 함 | P3-04 |
| 5 | 관리자 > 시뮬레이터 (실패 묶음) | 읽기 실패는 "변화 없음"이 아니라 수집 오류 | P3-02, P3-08 |
| 6 | 관리자 > 시뮬레이터 (예보·시세) | 사건 종류가 둘 이상 | P3-03 |
| 7 | 관리자 > 채점 결과 | 맞힌·놓친·잘못 울린 수 | P3-06 |
| 8 | 기록 찾기 | 끝난 알림을 찾고, 출처와 함께 답함 | P3-05 |
| 9 | 관리자 > 위키 챗봇 | 팀 문서(위키)만 근거로 답하고 출처를 보이며, 없으면 "위키에 없습니다" | P3-20, P3-21 |

시연 길이는 리허설로 정한다 [확인 필요]. 시간이 모자라면 장면 6·8·9를 줄이고, 2·3·4·5·7은 지킨다(CUJ-04의 핵심 순간이 2·3이다).

## 2. 시연 전 준비 (리허설 때 꼭 확인)

1. **접속**: 서비스 주소 https://homefit-lac.vercel.app (로그인해야 화면이 보인다). 관리자 계정과 가상(시험) 계정으로 각각 로그인한 창 둘을 미리 열어 둔다. 로그인 정보는 팀 비공개 채널에만 두고 이 문서와 슬라이드에는 쓰지 않는다.
2. **운영에 `SIMULATION_USER_IDS`가 들어 있는지 확인한다.** 없으면 시뮬레이터가 "대상 0곳"으로 돈다(qa 008 실패와 조치 3). 예림님이 2026-11-18에 Vercel에서 이 이름이 있는 것을 확인했다. 값이 가상 계정의 회원 ID와 맞는지는 리허설과 발표 직전에 다시 본다 [확인 필요].
3. **같은 묶음은 알림을 두 번 만들지 않는다**(spec 005 E3). 가상 계정에 이미 같은 알림이 있으면 "새 알림 0건"으로 나와 아무 일도 안 일어난 것처럼 보인다. 시연 전에 가상 계정의 열린 알림을 확인하고, 이미 있으면 다른 묶음(예: `changed` 대신 `correction`)을 쓴다. 알림을 지워서 비우는 방법은 데이터를 지우는 일이라 팀이 정한다 [확인 필요].
3-1. **가상 계정이 공고를 팔로우해 둔다.** 공고 사건은 팔로우한 맞는 공고가 바뀌었을 때만 생긴다(spec 001 FR-020, qa 001 C-062). 팔로우 없이 수집하면 변화만 읽고 사건은 0건이고, 처음 보인 공고도 사건이 생기지 않는다(qa 001 C-041). 순서는 ① `sample` 묶음으로 기준 공고를 저장하고 ② 가상 계정의 "맞는 공고"에서 하나를 팔로우(승인)한 뒤 ③ `changed`를 돌린다. **예림님이 확인한 현재 상태**(PR #14 코멘트, 2026-11-19): 가상 계정은 `SIM-BULK-1`(bulk 묶음) 말고 **`sample`의 `SIM-21581`도 2026-11-18 17:19에 팔로우**했다. 그래서 `changed`를 돌리면 사건이 0건이 아닐 수 있다. 어떤 사건이 몇 건 생기는지는 리허설에서 확인한다 [확인 필요]. 마감일이 3일 늦어진 변화를 만드는 `bulk-changed`도 쓸 수 있다(`watch/sim-fixtures.ts`). 운영 DB에 `sample` 기준 공고가 이미 있는지는 시연 전에 확인한다 [확인 필요]. 가상 계정에는 처리 대기 알림이 2건 있어서 같은 변화를 돌리면 "새 알림 0건"이 나올 수 있으니 리허설에서 확인한다(준비 3번).
4. **AI 요약**: 운영의 `AI_PROVIDER`와 키가 설정돼 있어야 요약이 나온다. 예림님이 2026-11-18에 Vercel에서 `AI_PROVIDER`와 `GEMINI_API_KEY`가 운영에 있는 것을 확인했고, 최근 이틀 AI 호출은 **Gemini 48건과 mock 6건**(위키 챗봇·로컬 시험)이라고 했다(PR #14 코멘트, 2026-11-19). DB를 로컬과 같이 써서 운영만 따로 셀 수는 없다. `ANTHROPIC_API_KEY`는 운영에 없어서 Claude로 바꾸려면 넣어야 한다. `AI_PROVIDER`의 정확한 값은 확인하지 못했다 [확인 필요]. 키가 없거나 AI가 실패해도 기본 체크리스트와 승인·거절 버튼은 나온다(qa 001 C-032). 예림님은 AI 요약을 보여 주는 쪽을 추천했고, 최종은 팀이 정한다 [확인 필요].
5. **끝난 알림이 있는 계정**: 장면 8(기록 찾기)은 승인·거절로 끝난 알림이 있어야 보인다. 장면 4에서 만든 것을 쓴다.
6. **슬랙 DM**(선택): 보여 주려면 가상 계정에서 알림을 미리 켜 둔다(qa 001 H-005에서 실제 DM 확인).

## 3. 순서

### 장면 1. 수집 현황 — 정기 수집이 쌓이고 있다
- 화면: 관리자 메뉴 > **수집 현황·오류** (`/admin/watch`)
- 한다: 출처별 마지막 실행과 **연속 실패 횟수**를 보여 준다. 기상청 같은 출처의 **"지금 한 번 실행"**을 눌러 기록이 한 줄 늘어나는 것을 보여 준다.
- 말한다: "정해진 시각에 저절로 수집하고, 실패하면 여기서 연속 실패가 보입니다."
- 근거: spec 005 FR-001, qa 005 C-501. 정기 실행 시각은 `vercel.json`(UTC 설정을 한국 시각으로 바꾸면 09:00·09:10·05:30·17:30, 매월 2일 10:00).

### 장면 2. 시뮬레이터 — 가짜 공고를 넣는다
- 화면: **시뮬레이터** (`/admin/sim`) > "마이홈 가짜 공고"
- 한다: (준비 3-1을 마친 상태에서) 묶음 **`changed`**를 고르고 실행한다. 결과 요약(성공, 읽은 공고 수, 새 알림 수)과 **흐름 화면 링크**를 보여 준다. 새 알림이 1건 생기면 성공이다.
- 말한다: "실제 공고를 기다리지 않고, 정답이 붙은 가짜 묶음으로 같은 경로를 돌립니다. 알림은 가상 계정에게만 생기고 실제 계정에는 생기지 않습니다."
- 주의 1: 준비 3번(같은 묶음 두 번 → 새 알림 0건).
- 주의 2: `changed`는 **마감일만 하루 늦춘다.** 월세와 공급 유형은 바뀌지 않는다(`watch/sim-fixtures.ts`의 `changed`는 모든 공고의 `endDe`(접수 종료일)에 1일을 더한다). 시뮬레이터 화면 문구도 PR #8(`f128f98`)에서 "마감일이 하루 늦음 → 알림"으로 고쳐져 이제 동작과 같다(`app/(main)/admin/sim/page.tsx`). 다만 운영 배포는 따로다. 예림님이 2026-11-18에 확인한 대로 **운영 화면은 PR #8 배포 전이라 아직 옛 문구("마감일·월세가 바뀜")가 보인다.** 배포하면 고쳐지고, 그때까지 시연하면 화면 문구가 아니라 실제 동작을 따른다. 발표에서는 "마감일이 하루 늦어졌습니다"라고 말한다. 알림 상세의 "무엇이 바뀌었나"에 마감일 전 → 후가 보이는지는 리허설에서 확인한다(qa 001 C-047은 마감일 변경 화면을 확인함).
- 근거: CUJ-04 1단계, spec 005 FR-002, qa 005 C-502.

### 장면 3. 흐름 화면 — 실제로 돈 기록이다
- 화면: **흐름 화면** (`/admin/flow`)
- 한다: 방금 실행을 고른다. 시작 상자 4종(마이홈 공고, 기상청 예보, 온통청년 정책, 실거래가. `flow/graph.ts`의 `SOURCES`), 단계 상자와 화살표, 상태 글자(성공·실패·승인 대기·건너뜀), 들어온·나간 건수를 보여 준다. **상자 하나를 열어** 입력·출력 건수와 상세를 보여 준다. 기록이 없는 출처는 "아직 안 켜짐"(회색)이다.
- 말한다: "미리 그린 그림이 아니라 실행 기록(runs, run_steps)에서 그립니다. 상세에는 비밀 키가 가려져 있습니다."
- 근거: CUJ-04 2·3단계(핵심 순간), spec 005 FR-003, qa 005 C-504.

### 장면 4. 사용자 쪽 — 승인해야 일정에 들어간다
- 화면: 가상 계정으로 로그인한 창 > 홈, **사건 상세**, **내 일정**
- 한다: 새 알림 > 상세의 "무엇이 바뀌었나", 요약과 계획 초안(체크리스트) > **승인** > 내 일정에 체크리스트와 마감일이 들어간다. 같은 시점에 관리자 쪽 **사건 현황**(`/admin/incidents`)과 **회원**(`/admin/users`)에는 **승인 버튼이 없는 것**을 보여 준다.
- 말한다: "사람이 승인하기 전에는 아무것도 바뀌지 않고, 관리자도 대신 승인하지 못합니다."
- 근거: CUJ-04 4단계, spec 005 FR-005, qa 001 H-007.

### 장면 5. 실패 장면 — 읽기 실패는 수집 오류다
- 화면: **시뮬레이터** > 묶음 **`failure`**(API 실패) 또는 **`malformed`**(모양이 깨진 응답) 실행 > **흐름 화면** > **수집 현황·오류**
- 한다: 실행 요약이 실패로 나오고, 흐름 화면에서 실패 상자가 보이며 그 뒤 단계에는 도달하지 못한 것을 보여 준다. 수집 현황의 **최근 실행 표에 "시뮬레이터 · 수집 오류" 한 줄**이 생기는 것을 보여 준다(시뮬레이터 실행은 연속 실패 수에 들어가지 않아 그 수는 그대로다). 상세의 오류 문구에서 키 값이 가려져 있는 것도 보여 준다.
- 말한다: "읽기에 실패하면 '변화 없음'으로 두지 않고 수집 오류로 기록합니다."
- 근거: CUJ-04 2단계 인사이트("실패 장면도 시연에 넣는다"), qa 001 C-017. 실패 처리 설명은 `docs/data-sources.md` 4절(조각 C1, PR #5가 합쳐진 뒤 링크를 잇는다).

### 장면 6. 사건 종류를 늘린다 — 습도·결로, 시세
- 화면: **시뮬레이터** > "기상청 가짜 예보" **`cold`**("추운 밤 + 높은 습도 → 결로 위험"), "실거래가(시세) 가짜 거래" **`rise`**("같은 조건 거래 6건, 월세·보증금이 기준보다 20% 높음 → 알림")
- 한다: 각각 실행하고 흐름 화면에서 시작 상자가 바뀌는 것을 보여 준다. 가상 계정의 알림에서 습도 사건 상세, 시세 비교표를 한 번씩 연다.
- 선택: 시세 묶음 **`live`**는 국토부 실제 거래를 가상 계정의 집·관심 지역에만 비교한다(실제 API 연결 시연). 호출 한도를 확인하지 못했으니 [확인 필요] 리허설에서만 쓴다.
- 말한다: "공고, 습도·결로, 시세. 사건 종류가 세 가지이고 같은 구조로 돕니다."
- 근거: CUJ-04 검증("가짜 묶음 3종과 실패 1종을 한 번씩 돌린다"), spec 003, spec 008.

### 장면 7. 채점 — 숫자로 증명한다
- 화면: **채점 결과** (`/admin/eval`)
- 한다: 정답이 붙은 가짜 묶음 28건의 결과 **맞힘 11, 놓침 0, 잘못 울림 0, 조용히 맞음 17**(공고 10, 습도 8, 시세 10)을 보여 주고 사례 줄을 연다.
- 말한다: "알려야 할 것을 알리고, 알리지 않아야 할 것은 조용히 있었는지를 정답과 비교합니다."
- 주의: 이 숫자는 2026-11-18 생성 파일(`eval/results.json`) 기준이다. 시세 묶음 10건은 조각 B(PR #11)에서 들어왔다. 운영 화면에 이 숫자가 반영됐는지(배포)는 확인하지 못했다 [확인 필요]. 발표 직전에 `npm run eval`을 다시 돌려 화면과 파일 숫자가 같은지 확인한다 [확인 필요].
- 근거: CUJ-04 5단계, spec 005 FR-004, qa 005 C-505.

### 장면 8. 기록 찾기 — 지난 처리에서 근거를 꺼낸다
- 화면: **기록 찾기** (`/knowledge`)
- 한다: 승인·거절로 끝난 알림을 낱말로 찾고, 결과의 알림 링크·처리 결과·날짜를 연다. 질문으로 물으면 찾은 기록만 근거로 답하고 출처 링크가 붙는다. 근거가 없으면 "기록에서 찾지 못했습니다"가 나온다.
- 말한다: "끝난 알림을 찾아서, 지난 처리를 근거로 다시 꺼내 볼 수 있습니다."
- 주의 1: **알림 상세의 "비슷한 지난 알림"은 조각 B(PR #11)로 들어왔다.** 알림 상세에서 내 알림 가운데 같은 종류로 끝난(승인·거절) 알림을 **제목 낱말이 겹치는 순으로 최대 3개** 보여 주고, 겹치는 낱말이 없으면 "비슷한 지난 알림이 없습니다"가 나온다. AI가 찾는 것이 아니고 임베딩도 쓰지 않으므로 "낱말이 겹치는 순으로 찾는다"고 말한다(평가 항목 P3-05의 "RAG"라고 말하지 않는다). 끝난 알림이 있는 계정이어야 보인다(준비 5). 운영에 배포돼 화면에 나오는지는 리허설에서 확인한다 [확인 필요].
- 주의 2: qa 005 C-507은 "부분 통과"다(끝난 알림이 없는 계정이라 찾은 기록이 있는 화면과 AI 답은 못 봄). 장면 4에서 끝낸 알림으로 리허설한다.

### 장면 9. 위키 챗봇 — 팀 문서에서 근거를 꺼낸다
- 화면: **위키 챗봇** (`/admin/chat`, 관리자만. 일반 계정은 "관리자만 볼 수 있습니다"). 조각 A(PR #15)가 2026-11-19 10:11에 `main`에 합쳐졌다.
- 한다: 질문 칸에 정답표(`docs/wiki-chat.md` 1절)의 질문을 하나씩 넣는다. **세 갈래를 한 번씩** 보인다(질문은 정답표 6개 중에서 고른다).
  1. **위키에 답이 있는 질문** — 예: "관리자도 사건을 대신 승인할 수 있어?"(Q1). 정답은 "못 한다, 관리자 화면에는 승인 버튼이 없다". 답 아래 **출처 쪽**을 눌러 그 절 내용이 펼쳐지는 것을 보인다.
  2. **위키에 없는 질문** — 예: "대표님 점심 메뉴는?"(Q4). "위키에 없습니다"가 나오고 출처가 없다. 지어내지 않는다는 것을 보이는 장면이다.
  3. **문서끼리 어긋난 곳을 묻는 질문** — 예: "건축물 정보 조회는 1차 범위야?"(Q5). IA(보류)와 PRD(1차 조회)가 다르다는 것을 두 출처와 함께 답한다.
- 말한다: "챗봇은 우리 팀 문서(위키)만 근거로 답하고, 근거 쪽을 보여 줍니다. 근거가 없으면 모른다고 합니다. 문서끼리 어긋나면 둘 다 알려 줍니다."
- 주의 1: **하루 질문 한도가 20번**(관리자 한 명 기준. 하루를 한국 날짜로 센다는 것은 spec의 가정이다)이다. 한도를 넘으면 "오늘 질문 한도를 다 썼습니다"가 나오고 AI를 부르지 않는다. 화면에 **오늘 남은 질문 수**가 보이니 리허설에서 질문을 아끼고, 발표에서는 3~4개만 쓴다. 질문은 1~300자, 답은 600자 안이다.
- 주의 2: 화면에 **"모의 답 · 실제 AI 답이 아닙니다"**가 보이면 AI 설정이 없어 모의(mock)로 돈 것이다. 모의 답은 실제 답 품질을 보여 주지 않으니 발표에서는 쓰지 않는다. 운영에서 실제 AI(`AI_PROVIDER`·키)로 답이 나오는지 리허설에서 확인한다 [확인 필요].
- 주의 3: **실제 Gemini로 정답표를 돌린 결과는 `docs/wiki-chat.md` 2절에 기록돼 있다**(PR #24, 2026-11-19, `gemini-3.5-flash-lite`). 정답표 6문항 중 6개 맞음(Q2는 "맞음(조건 일부 생략)")이고, 숨은 지시("바나나")는 따르지 않았다. 다만 **Q5·Q6 정답 문장은 이 결과 뒤에 원본(PRD v1.10·IA v1.8)에 맞춰 고쳤고, 첫 결과표는 옛 정답 기준**이라 새 정답으로 다시 돌려야 한다(`wiki-chat.md` 1절). 또 **확인 스크립트로 한 번 돌린 결과**이고 운영 화면에서 직접 물어본 기록은 아니다. 그래서 발표에서는 "정답표 6문항을 확인 스크립트로 돌렸을 때 옛 정답 기준으로 모두 맞았다, Q5·Q6은 새 정답으로 다시 돌릴 예정"까지만 말하고, 운영 화면의 실제 답은 리허설에서 세 질문을 물어 확인한다 [확인 필요]. "정답률 N%"는 말하지 않는다.
- 주의 4: 이 화면이 **운영에 배포됐는지는 확인하지 못했다**(PR #15는 `main`에 합쳐졌을 뿐이다). 운영 DB에는 `chat_logs` 표가 이미 있다(현경님이 SQL Editor로 적용). 배포 전이면 `/admin/chat`이 옛 화면(질문 입력이 막힌 자리)일 수 있다 [확인 필요].
- 주의 5: 질문은 `chat_logs`에 **기록**되고 지워지지 않는다. 발표 질문에 개인정보·키를 넣지 않는다.
- 근거: spec 012 FR-009~016, `docs/wiki-chat.md` 정답표, PR #15 설명, 평가 항목 P3-20·P3-21.

## 5. 확인하지 못한 것 / 정할 것

- 운영 주소에서 위 순서를 **처음부터 끝까지 돌려 본 기록이 없다.** 리허설을 하고 결과를 `docs/specs/005-관리자-시연-기록찾기/qa.md`의 사람 QA 항목 H-501에 팀이 적는다(H-501·H-502 결과 칸은 비어 있고, AI가 대신 통과로 적지 않는다).
- spec 005의 상태가 **"초안 v0.1 (승인 전)"**이다. 시연의 중심 기능이 승인 전이니 팀이 승인할지 정해야 한다.
- 운영 DB에 기준 공고(`sample`)가 있는지, 가상 계정이 팔로우한 공고가 있는지(준비 3-1)를 시연 전에 확인한다.
- 시뮬레이터 화면 문구 "마감일·월세가 바뀜"은 PR #8에서 "마감일이 하루 늦음 → 알림"으로 고쳐졌다. 운영 화면은 PR #8 배포 전이라 아직 옛 문구다(예림님 확인, 2026-11-18). 배포하면 고쳐진다.
- 시연 길이, 맡을 사람(누가 화면을 누르고 누가 말하는지)은 정하지 않았다. 장면 9(위키 챗봇)를 시연에 넣을지, 넣으면 누가 맡을지도 팀이 정한다(조각 A는 현경님).
- 가상 계정으로 로그인하는 방법과 정보는 이 문서에 쓰지 않았다(비밀). 팀 비공개 채널에서 받는다.
- 운영(Vercel)에 `AI_PROVIDER`, `GEMINI_API_KEY`, `SIMULATION_USER_IDS`가 있는 것은 예림님이 2026-11-18에 확인했다. `ANTHROPIC_API_KEY`는 운영에 없다. `AI_PROVIDER`의 정확한 값과 `SIMULATION_USER_IDS`가 가상 계정과 맞는지는 확인하지 못했다. 가상 계정은 `SIM-BULK-1`과 `SIM-21581`을 팔로우하고 처리 대기 알림이 2건(공고 1, 시세 1) 있다(예림님 확인, 준비 3-1).
- 슬라이드의 "시연(실패 장면 포함)"과 "채점" 장은 이 순서의 장면 5, 7과 맞춘다. 슬랙 알림 DM을 넣을지는 팀이 정한다. 위키 챗봇은 장면 9로 넣었고(PR #15 합쳐짐), 실제 Gemini 결과는 `docs/wiki-chat.md`에 기록됐고(PR #24), 운영 배포와 운영 화면의 실제 답은 확인해야 한다.

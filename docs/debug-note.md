## 3. 실패 → 규칙 반영 → 재검사 사례 (P3-26)

### 사례 1. 빌드를 빼먹어 운영 빌드가 실패함
- **실패**: 2026-11-18 운영 빌드 실패. `/policy/[id]`의 정책 탭이 주소를 읽는 부분이 Suspense 밖이었다. "커밋 전에 빌드를 돌리지 않았다"고 qa에 적혀 있다 (qa 006 #2). 같은 종류의 오류가 이미 qa 004 #4(사이드바), qa 005 #3(관리자 탭)에서 두 번 나왔다.
- **조치**: 정책 탭을 Suspense로 감쌈 (커밋 `b189e39`).
- **규칙 반영**: `docs/plan.md` 2절에 "커밋 전에 넷 다 통과: `npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run build`"를 적고 이유로 이 실패를 달았다 (커밋 `826b696`).
- **재검사**: 2026-11-18 운영에서 정책 목록 49건, 종류 버튼 5개, 상세 요약이 보이는 것을 확인했다 (qa 006 #2 재확인 칸).
- **아직 못 한 것**: 규칙을 적은 뒤에 올라온 새 기능 PR에서 빌드가 지켜졌는지는 확인할 기록이 아직 없다. 다음 PR에서 확인한다.

### 사례 2. 배포 직후 수집이 옛 배포로 가서 사건이 잘못 생김
- **실패**: `npm run deploy` 직후 수집이 새 배포가 아니라 옛 배포를 가리키던 운영 주소로 갔다. 옛 규칙(v0.1)으로 사건 7건이 생겼다 (run `ab212ebe`, 2026-11-17, qa 001 #20).
- **조치**: 잘못 생긴 사건 7건과 계획 7개를 삭제했다(사용자 승인). `scripts/deploy.mjs`가 운영 주소가 새 배포를 가리키는지 `vercel inspect`로 10초마다 최대 12번 확인한 뒤에만 수집하고, 확인하지 못하면 수집하지 않는다 (커밋 `1b0f792`).
- **재검사**: 시험 5개를 먼저 쓰고(`tests/deploy.test.ts`), 전체 시험 241개 통과. 운영 주소로 별칭 확인 함수가 새 배포는 참, 다른 배포는 거짓으로 답했다.
- **아직 못 한 것**: "다시 배포해 끝까지 돌려 보지는 않음"이라고 qa에 적혀 있다.

### 사례 3. 채점에서 정답 샘플이 틀려 있었음
- **실패**: 감지 채점에서 정답 묶음 N-07이 "놓침"으로 나왔다. 감지 코드가 아니라 정답 쪽 단지 키를 "가짜단지"로 적은 것이 원인이었다(규칙은 "시군구:단지명"). (qa 005 #1)
- **조치**: `eval/cases.ts`의 단지 키를 고쳤다.
- **규칙 반영**: 없음. 정답 샘플만 고쳤고, 정답 묶음을 쓸 때의 단지 키 규칙을 문서나 규칙 파일에 따로 적지는 않았다. P3-26의 근거는 사례 1·2이고, 이 사례는 채점에서 생긴 일을 있는 그대로 남긴 것이다.
- **재검사**: 같은 날 통과로 확인했다. 안내서 6절의 "틀린 사례를 정답 샘플에 먼저 반영하고 통과할 때까지 돌린다"는 방식과 같은 흐름이다.

- **조치**: main의 뼈대 커밋을 `Yelim`에 "기록만 합치는" 병합 커밋으로 넣었다 (`92bad76`, "fd6c24d = ababd21과 같은 내용, PR #1 squash").
- **규칙 반영**: `docs/plan.md` 2절에 "PR을 합칠 때는 Create a merge commit(squash 하지 않기). squash하면 같은 이름 브랜치를 다시 쓸 때 충돌이 난다(2026-11-18 PR #1 사례)"를 적었다 (커밋 `6c4e849`).
- **재검사**: 기능 001~008을 `Yelim`에서 main으로 합친 PR #4가 병합 커밋(부모 2개)으로 합쳐졌다(`65ed611`, gaangstar님 승인·병합). 규칙대로 squash를 쓰지 않았다. 합치는 중에 충돌이 있었는지는 기록에서 확인하지 못했다.

## 6. 이 문서에서 확인하지 못한 것
- 각 qa의 "재확인" 날짜가 실제로 그날 실행한 결과인지는 qa 표를 믿고 옮겼다. 직접 다시 돌려 보지 않았다.
